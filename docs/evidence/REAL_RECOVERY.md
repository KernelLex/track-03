# One real rupee: a rail-confirmed recovery, end to end

**2026-09-01.** A real Razorpay invoice, paid for real in test mode, whose
capture reached the live server as a real Razorpay-triggered webhook and
was attributed as recovered money under Law 7 — by the deployed service,
not by a script on my laptop.

This is the one thing `docs/RESULTS.md` could not previously claim. Its own
words: recovery there is "a modelling convention for my harness, not Law
7's real rail-confirmed-capture standard." That was accurate and it was the
weakest point in the project — the evaluation measured the pipeline's
judgment against a simulator's own ground truth, and no rupee had ever
crossed the rail. This document is n=1 against the real standard.

## What happened, in order

| When (UTC) | What | Id |
|---|---|---|
| 15:11 | Invoice created via `RazorpayRail.create_invoice()` | `inv_TWot3b6dnApicP`, ₹42,500 |
| ~15:20 | Paid in Razorpay **test mode** by netbanking | — |
| 15:20:57.095 | `invoice.paid` delivered to the live endpoint | `TWou1yfCgyxQHc` |
| 15:20:57.170 | **Attributed to the recovery ledger** | see row below |
| 15:20:57.206 | `payment.captured` delivered to the live endpoint | `TWou1cPf4kddCB` |

The event ids are Razorpay's own (`TWou1cPf4kddCB`), not this project's
synthetic `evt_*` test ids — these were generated by Razorpay and
delivered over the public internet to
`https://track-03.onrender.com/webhooks/razorpay`, signed with the real
shared secret and verified by `verify_and_ingest()` before anything was
parsed.

## The ledger row

```
payment_id   pay_TWotxaQoLsHFOt
invoice_id   inv_TWot3b6dnApicP
debtor_id    debtor_pay_TWotxaQoLsHFOt
amount_paise 4250000                     (₹42,500)
rail_tag     razorpay
recorded_at  2026-09-01T15:20:57.170Z
```

Read out of the production Turso database, not a local file.

Three properties hold here, and none of them are enforced by the code that
wrote this row — they are `RecoveryLedger.attribute()`'s, which
`_maybe_settle` only calls:

- **Only a capture counts.** `payment_status != "captured"` raises
  `NotCaptured`. The failed attempt below never reached the ledger.
- **Counted once.** `UNIQUE(payment_id)` in the database decides, not
  application logic — so a redelivery can't double-count even if it gets
  past INGEST's own dedup.
- **Tagged with the rail that produced it** (Law 6): `rail_tag = "razorpay"`.
  A simulated capture could never be mistaken for this one.

## What is honestly *not* clean about this run

Three things, none of which I'd want a reader to discover for themselves.

**1. `debtor_id` is a derived placeholder, not a real id.** I set
`{"debtor_id": "debtor_acme_textiles", "invoice_id": "INV-2201"}` in the
invoice's `notes` specifically so attribution would use real merchant ids.
It didn't, and the reason is a real Razorpay behaviour worth recording:

```
invoice notes : {'debtor_id': 'debtor_acme_textiles', 'invoice_id': 'INV-2201'}
payment notes : []
```

**Razorpay does not propagate an invoice's `notes` onto the payment entity.**
The webhook carries the payment, so `agent/ingest/listen.py`'s notes
extraction — which is correct, and tested — simply had nothing to read.
The real `invoice_id` did come through, because a payment against an
invoice carries it as a first-class field. So this row is half real ids and
half placeholder, and the placeholder half is visible in it.

The two correct fixes, neither of which I've made yet because both are real
design decisions rather than patches: set the notes on the **order or
payment link** at creation time (those do propagate), or resolve the debtor
by fetching the invoice when only `invoice_id` is known. I've deliberately
not put a blocking rail call inside the webhook handler for the second —
`docs/SCALABILITY.md` already argues that handler should enqueue rather
than do slow work inline, and adding a synchronous fetch there would
contradict it.

**2. This is the second invoice, not the first.** The first real payment
(`pay_TWon6jEzqjqxLA`, `inv_TWoY4eT3fZMsfc`, also ₹42,500, also captured)
reached the server at 15:14:29 as real events `TWonCv6XXsT4xq` /
`TWonDIHProgPde` — and was **dropped**, because the SETTLE wiring hadn't
finished deploying. It was ingested and deduped correctly and then went
nowhere, which is exactly the gap this work closes.

I could have replayed that event once the deploy landed, and chose not to:
INGEST had already recorded its event id, so a replay would have been
correctly rejected as a duplicate, and deleting that row to force it
through would have meant presenting a manufactured delivery as an original
one. A second genuine payment costs nothing in test mode and is the honest
artifact.

**3. n=1, in test mode.** One payment, on a test-mode account, with no real
money. It demonstrates that the path works end to end under the real
standard; it is not a measurement of recovery rate, and nothing in
`docs/RESULTS.md` should be read as rail-confirmed on the strength of it.

## The failed attempt, kept deliberately

```
pay_TWoftiQ4eYjXKh | failed | 4250000 | inv_TWoY4eT3fZMsfc | card
```

The first card attempt was rejected by Razorpay: *"International cards are
not supported"* — `4111 1111 1111 1111` is an international test card and
this account only accepts domestic ones. Recorded here because it's a real
rejection from the real rail, and because the ledger's refusal to attribute
anything but a `captured` status is easier to trust when the non-captured
attempts are visible too.

## Reproducing the check

```
uv run python - <<'EOF'
import libsql, os
conn = libsql.connect(database=os.environ["TURSO_DATABASE_URL"],
                      auth_token=os.environ["TURSO_AUTH_TOKEN"])
for row in conn.execute(
    "SELECT payment_id, invoice_id, amount_paise, rail_tag, recorded_at FROM recovery_ledger"
).fetchall():
    print(row)
EOF
```

The corresponding Razorpay-side facts (`payment.fetch`, `invoice.fetch`)
are verifiable with the same test-mode keys.
